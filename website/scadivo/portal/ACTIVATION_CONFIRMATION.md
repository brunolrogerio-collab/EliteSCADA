All URLs below are under `/portal/api/licensing/device`. HTTPS required. No Portal cookie or CSRF token is used. Responses containing confirmation tokens or leases use Cache-Control: no-store. Signing stays disabled until joint product validation; preparation is available without signing, and reports `onlineActivationAvailable`.

## POST /prepare

JSON: `username` (Portal username or email), `password`, `licenseCode` (single public code), `activationId` (client-generated nonempty UUID), `machineFingerprint` (64 hex characters), and optional `currentRefreshCredential` (43-character Base64URL device credential). Send that credential only when the product has it for this local binding; omit it for a new activation or when local state requires account reauthentication. If supplied but invalid or no longer current, preparation fails closed and does not downgrade to account-only recovery. Machine and activation identifiers are device-generated, never user-entered internal organization/application IDs.

200: `confirmationToken` (256 random bits, Base64URL), `expiresAtUtc` (five minutes), `onlineActivationAvailable`, `summary`, `activationId` (canonical ID to use at confirm), `reactivation` (boolean), and `credentialGeneration` (nonnegative JSON integer represented as `int64`). For a new activation, the returned ID equals the requested ID, `reactivation` is false and generation is 0. For recovery, the Portal may resolve the unique existing activation and return its canonical ID. The product persists and uses this ID before confirming; IDs are never shown to users. Only the token hash is stored. Password is authenticated only here, never persisted in a preparation.

Summary: `licenseId`, `organizationId`, `applicationId`, `licenseCode`, `applicationName`, `mode` (`online-account`), `term` (`perpetual`, `monthly`, `annual`), `entitlementExpiresAtUtc` (nullable commercial expiry), `tier`, `interactiveSeats`, `viewOnlySeats`, `haRuntime`, `assetProcessIntelligence`, `maxActivations`.

Preparation checks confirmed/accepted/unsuspended account, membership and active unexpired license. If the requested ID exists, all account/license/organization/application/fingerprint bindings must match; incompatibility returns 409 `activation-recovery-unavailable` and never falls back to a new activation. If the ID does not identify a row, the Portal searches only this authenticated user's active or reauthentication-required activations with the exact license, organization, application and fingerprint: zero eligible matches follows the new-activation flow; one match resolves to recovery; multiple matches return 409 `activation-recovery-ambiguous`. A revoked matching activation is rejected with `activation-revoked`. A supplied current credential is hashed and checked against that exact activation's Current credential; a well-formed but incorrect or stale proof returns 409 `activation-recovery-unavailable` without fallback. Omitting the proof allows account reauthentication only after the user confirms the resolved summary. The preparation binds the canonical ID, recovery/new mode, fingerprint, account security stamp, rights snapshot, and credential generation. It creates no activation, credential or lease and does not reserve capacity. Display the summary and require explicit user confirmation before confirm. Recovery must clearly say that the same existing installation is being reauthenticated and its slot remains occupied. A commercial perpetual right still uses short online leases. Do not infer commercial term from lease TTL.

## POST /confirm

JSON: `confirmationToken`, canonical `activationId` returned by prepare, same `machineFingerprint`, `requestId` (client-generated nonempty UUID), `refreshCredential` (client-generated 32 random bytes encoded as 43 Base64URL characters). Generation is bound to the preparation and is not sent again. Persist the request intent securely before sending, so a lost response can be retried with exactly the same fields.

200: `activationId`, `lease`, `notAfterUtc`, `summary` (same prepared snapshot). No password. User/security stamp, membership, current license and application summary are revalidated under database locks. Changes to prepared rights or presentation require preparing again; no silently changed grant. New activation checks capacity and commits token consumption, activation and hashed refresh credential in one transaction. Recovery locks and revalidates the existing row and generation, rotates the credential and lease, and preserves the same row, activation ID, fingerprint and occupied slot; it does not revoke, rebind or increase capacity.

An exact retry (including after a lost response, client restart, or a later credential rotation) returns the original lease stored against that consumed preparation. Simultaneous recoveries from one generation serialize: only the first can rotate; stale confirmation fails with `activation-recovery-invalidated` and does not revoke the winning credential. On recovery, all earlier Current/Superseded device credentials are marked `recovered` so a delayed old credential cannot be misclassified as theft of the new credential. A consumed token cannot authorize another request or refresh credential. First confirmation must occur within five minutes; exact retries are retained until 24 hours after token expiry. Old rows are removed on subsequent preparation.

## POST /cancel

JSON: `confirmationToken`. Returns 204, including unknown token. Marks an unconsumed preparation cancelled. Cancellation after successful confirmation does not revoke an activation. Cancellation and confirmation serialize on the preparation row; whichever commits first determines the result. Abandoning or cancelling an unconsumed preparation costs no activation slot.

## Errors

400: invalid input (`invalid-input`) or `https-required`. 401: `invalid-credentials` for account authentication/unknown token. 404: license eligibility failures return `license-not-available`. 409: `preparation-invalidated` (cancelled, changed account stamp/summary or machine/activation mismatch), `preparation-expired`, `preparation-already-consumed`, `activation-revoked`, `activation-already-active`, `activation-limit-reached`, `activation-recovery-ambiguous` (multiple exact candidates), `activation-recovery-unavailable` (existing ID binding or supplied proof mismatch), `activation-recovery-invalidated` (generation/proof changed after prepare), `refresh-credential-already-used`, or `activation-request-conflict`. 429: throttled. Confirm returns the existing 503 signing-unavailable response while issuance is disabled. Old POST /activate returns 410 `activation-confirmation-required` and cannot bypass confirmation.

## Signed rights and renewal

The ESLEASE1 schema and its 14 claims are unchanged. Summary is HTTPS presentation metadata, not additional signed rights. Product must verify signature, identity, machine, tier, seats, flags and times against the lease and reject mismatches before committing local installation. Commercial term/name are not claims and cannot expand signed rights. Renewal remains the existing Bearer rotating-device-credential endpoint, automatic at 48 hours with maximum 72-hour leases. It does not use a Portal browser session or resubmit the account password. Password changes invalidate prepared tokens through the security stamp and existing activation credential invalidation.

No production deployment, signing-key provisioning or issuance activation is part of this change. Product integration remains under #301; Portal scope #741. This branch is based on integrated Portal main `c6bd3bf6`; it does not include changes to the product's recovery screen or activation client.
