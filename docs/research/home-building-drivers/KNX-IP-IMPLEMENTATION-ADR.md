# Wave 15 home-building protocol closeout: KNX/IP Secure v1

**Status:** Implementation authorized by the project coordinator on 2026-10-12; local implementation and verification are in progress. Acceptance, integration and freeze remain contingent on the exact PR-head T1 evidence. **Scope:** KNX/IP Secure tunnel plus the existing Native Zigbee and DALI profile closeout. This ADR records an implementation path for the already selected contracts; it does not reopen the FND-02, AUTH-03, AUTH-04, Zigbee, DALI or KNX qualifications.

## Decisions

1. **Reuse the converged driver/runtime boundary.** Register the KNX planner, factory and descriptor through `CommunicationDriverRuntimeComposition.BuildForCurrentSchema`; invoke it through the existing `EngineeringDriverCatalogApi.AddEngineeringDriverCatalog` registration. The implementation consumes canonical Data Source, CommunicationBinding, TAG cache, event and readiness paths. It adds no protocol-specific runtime or alternate activation path.
2. **Keep policy and credentials Authority-owned.** `IntegrationProtectedMaterialEndpoints.MapIntegrationProtectedMaterialEndpoints`, `IntegrationProtectedMaterialScopePolicy` and `HostAuthorityDriverMaterialResolver` provision and resolve the three existing KNX purposes, scoped to the stable project and Data Source ID. Engineering packages contain only `HostMaterialSlotReference.Marker`; raw secrets, password hashes and `.knxkeys` files never enter `.escadapkg`, logs or diagnostics.
3. **Use exactly one secure connection mode.** XKNX `3.20.0` runs in the managed `CPython 3.13.x` sidecar on Windows x64 and Linux x64. `create_xknx_connection` creates `ConnectionType.TUNNELING_TCP_SECURE` explicitly. The runtime rejects an absent/mismatched keyring slot, credentials, or Data Secure group key; it does not discover gateways or fall back to UDP, routing, automatic selection or plaintext. `parse_keyring_bundle` validates the ETS keyring signature and decrypts in memory.
4. **Bound the initial protocol profile.** Driver type is `knx.ip`; the versioned TAG binding is `elitescada.driver.knx.ip` v1. Supported DPTs remain `1.001`, `1.002`, `5.001`, `9.001`, `9.004`, `9.007`, and `9.024`. Command/write and authoritative status/readback group addresses remain distinct. A command transmission is not process truth: only accepted write plus a secure readback, or a received Data Secure status telegram, may update the canonical TAG value.
5. **Preserve sidecar lifecycle and fail-closed behavior.** `KnxIpCommunicationRuntimeFactory` resolves host Protected Material via the existing managed-sidecar binding. Its one-line UTF-8 bootstrap frame is sent over stdin as a bounded byte buffer and zeroed after the write; credentials and keyring data never enter the process environment. `KnxIpRpcServer` authenticates the child over loopback using a fresh random token, checks its artifact/runtime/schema identity, and accepts only bounded messages for configured TAGs. A write requires explicit acceptance and a valid returned state value. Standby cannot start the connection or issue writes.
6. **Keep dependency and platform claims precise.** The runtime dependency closure is hash-locked in `requirements.lock` and described in `SBOM.cdx.json`; CI exercises CPython 3.13.16 on Windows x64 and Linux x64. Python packages are not vendored into the API publish output; host administrators provision a dedicated venv. The dependency lock is verified for both platform wheel sets.
7. **Retain the DALI boundary.** DALI v1 remains the Intesis 700 DALI-2 profile over the existing `modbus.tcp` driver, not a new native DALI protocol stack. See `docs/examples/home-building/INTESIS-700-DALI-2-PROFILE.md`. Physical gateway/ballast L4 remains separate from T1 software evidence.
8. **Treat Zigbee separately from bridges.** `zigbee.native` is the Native CC2652 host-resource sidecar; `zigbee2mqtt` remains the separately managed gateway/MQTT integration. The selected implementation runs on supported Windows and Linux x64 hosts; no platform-specific serial path is placed in Engineering packages.

## Evidence and release gate

Local verification includes planner/fail-closed tests, the authenticated RPC and accepted-write contract, old/canonical TAG publication behavior, Python keyring/configuration/DPT/secure-telegram tests, hash-locked dependency installation, and Windows/Linux CI. Do not claim a physical KNX gateway smoke test, Zigbee hardware qualification, or DALI ballast L4 without the corresponding device evidence. Keep the prior KNX qualification issue's wait/authorization history intact; the coordinator's explicit implementation authorization releases product-code work but does not silently change the frozen limits. The handoff/PR must cite the exact source HEAD and the T1 run IDs/results; no step after this closeout is authorized before the exact PR head is integrated and its post-merge gate passes.
