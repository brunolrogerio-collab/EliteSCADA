# EliteSCADA v0.1 — Full Product Validation Preview

Status: **LOCKED PRODUCT ROADMAP TO FIRST OWNER VALIDATION**  
Approved by product owner: 2026-08-27.

This document defines what the first true owner-facing EliteSCADA validation version must prove and the ordered Development Waves required to reach it.

It supersedes any earlier interpretation that the first owner-facing validation package may be delivered before Client Visual Python and functional graphical Engineering exist. Internal CI/development packages may exist earlier, but they are not the v0.1 product validation preview.

## Product gate

The decisive v0.1 flow is:

```text
Engineering
  -> project/Data Source/TAG/Alarm/History
  -> TAG bit selectors / physical bit bindings
  -> Screen/Popup/Dynamo
  -> objects
  -> bindings/expressions
  -> Historical Data / Report definitions
  -> Client Visual Python behavior
  -> Save/Revision
  -> Publish
  -> Activate
  -> Runtime
  -> report preview/print/export
  -> restart/recovery of the Active Revision
```

The product owner must be able to construct and use a real small/medium-complexity supervisory application through the product, without editing database rows or private renderer JSON.

A demo that requires manual hidden configuration is evidence of a product gap, not acceptance evidence.

# WAVE 08-FOLLOW-A — TAG bit access + driver bit-level Boolean binding

This follow-up is mandatory after the current Wave 08 interaction work is integrated. It is a prerequisite for visual expressions that use bit selectors such as `Word_status.03`.

Canonical contract: `docs/TAG-BIT-ACCESS-AND-BIT-BINDING.md`.

### Product objective

Make bit-oriented PLC/driver data usable without forcing engineers to create private masks or scripts:

- integer TAG bit selectors with preferred notation `<TAG>.NN`;
- stable canonical reference as TAG identity + bit index;
- Int16/Int32/Int64 fixed-width bit ranges, LSB = bit 0 and signed two's-complement semantics;
- source quality/timestamp inheritance rather than bad quality becoming false;
- Boolean use in bindings, alarms, scripting/reference surfaces and later visual expressions;
- first-class Boolean TAG physical bit binding when a driver supports word/register bit selection;
- Modbus Holding/Input Register bit `0..15` read semantics;
- safe writable Holding Register bit mutation that preserves unrelated bits;
- native Modbus Mask Write Register where supported or coordinated concurrency-safe read-modify-write otherwise;
- poll sharing/coalescing for multiple bit TAGs on the same register where practical;
- explicit human 4xxxxx vs zero-based Modbus wire-address policy;
- canonical import/export/revision/package fidelity and normal authorization/Audit;
- permanent conformance rule requiring later drivers with bit-addressable storage to expose structured bit reads and safe bit writes wherever the underlying protocol/address is writable.

### Follow-up gate

The integrated product must prove at minimum:

`integer TAG -> .NN bit selector -> Boolean reference with inherited quality`

and:

`Modbus Holding Register -> Boolean bit TAG -> read/write one bit without corrupting other bits`

A logical bit selector is a view, not automatically another historian series. First-class Boolean bit-bound TAGs are used when independent history/alarm identity is required.

# WAVE 08-FOLLOW-B — typed visual expressions + boolean conditions + Analog Fill

This follow-up is mandatory after TAG-bit semantics are stable and before Wave 09 activates. It does not retroactively broaden active worker assignments.

Canonical contract: `docs/VISUAL-BOOLEAN-CONDITIONS-AND-ANALOG-FILL.md`.

### Product objective

Make ordinary HMI presentation logic declarative without forcing Python:

- typed side-effect-free visual expressions over canonical TAGs and Client Memory;
- integer TAG bit selectors such as `Word_status.03` as Boolean expression dependencies;
- boolean `and`/`or`/`not`, comparisons and parentheses;
- numeric arithmetic with normal precedence, including formulas such as `(nivel1 + nivel2) * 3`;
- explicit boolean/numeric conversions, never silent coercion;
- bounded pure helper whitelist;
- canonical dependency resolution and reactive reevaluation;
- universal `visible` for renderable visual objects;
- direct boolean, numeric interval and typed-expression modes for boolean properties;
- Analog Fill for supported closed shapes using raw numeric bindings or numeric expressions;
- engineering min/max scaling, four initial fill directions and explicit fill color;
- full canonical import/export/revision/package fidelity;
- bounded evaluator with no arbitrary JavaScript/Python/user code or direct driver/database/network/DOM access.

### Follow-up gate

The integrated product must prove at minimum:

`TAGs/Client Memory/bit selectors -> typed expression -> compatible visual property -> save/reopen -> export/import -> Runtime reevaluation`

and:

`numeric binding/expression -> Analog Fill scale -> proportional rendered fill`

Bad/unavailable dependencies must fall back through normal property precedence with diagnostics rather than silently forcing false/zero. Runtime-calculated expression/condition/fill results are presentation state, not saved Engineering values. Visual expressions remain presentation behavior and never process safety/interlock authority.

# After v0.1

Only after owner validation/corrections does the major external protocol expansion open.

Preferred sequence remains:

`MQTT reference implementation -> OPC UA -> BACnet -> Driver Module framework -> Siemens S7 -> Allen-Bradley`

The first new protocol, MQTT, should prove the converged Driver SDK in one coordinated wave rather than assigning three unrelated new protocol implementations simultaneously. Later protocols may parallelize only after the common Driver SDK/module/Engineering patterns have been proven by production code.

Every later production driver that exposes bit-addressable word/byte/register storage must comply with the permanent bit-level contract: structured bit read support and safe unrelated-bit-preserving write support wherever the protocol/address is writable, with read-only areas remaining explicitly read-only and common conformance tests required.

Advanced visual libraries, Dynamos, Trends, Engineering Fragments, assets, Server Python, distributed/scheduled Reporting and public SDK/module capabilities continue after or alongside later gates according to dependencies.
